# 調査の共通ブリーフ (2026-10-24)

## 目的
Desktop の OS / 構成手段の候補を、制約 (同じフォルダの desktop-v3.md 3章) ごとに採点するための**事実**を集める。採点はしない。事実と出典だけを集める。

## 対象ハード (G-HW)
i7-7700K、RAM 16GB、RTX 3060 Ti 8GB (GPU は1枚、iGPU は無効)、1080p144 が2画面、JIS キーボード、NVMe 1TB + HDD 2TB、UEFI で Secure Boot は今有効 (無効にもできる)。

## 選好 (P、固定)
コンポジタは niri、シェルは DankMaterialShell (DMS)、日本語入力は fcitx5 + hazkey (mozc が補助)、ターミナルは ghostty、ブラウザは zen。推論ランタイムは未定 (llama.cpp か ollama を想定。OpenAI 互換 API を出す)。

## 守ること
- 出典は**一次情報だけ**: 公式ドキュメント、公式 wiki、公式リポジトリ (README、docs、リリースノート、issue)、ディストリの公式パッケージ情報、メーリングリスト、公式ニュース。アフィリエイトサイト、SEO 目的のまとめ記事、個人ブログのランキング記事は使わない。フォーラムや Reddit は使わない (どうしても要るときは「一次でない」と明記する)。
- 確認できなかったことは「未検証」と書く。推測で埋めない。推測を書くときは [推論] と付ける。
- **鮮度の数値 (版、リリース日、遅延の日数) は集めなくてよい。** 別のスクリプトで測る。ただし「その部品が公式の経路で配布されているか、どの経路か (公式リポジトリ / COPR / AUR / flake / OBS など)」は集める。
- 調べるのは下の制約に関係する事実だけ。範囲を広げない。

## 集める観点 (制約 ID)
- FUN-1: niri / DMS / fcitx5-hazkey / ghostty / zen が、どの経路で入るか。NVIDIA + Wayland + niri の既知の問題。
- FUN-3: NVIDIA ドライバ (open カーネルモジュール) と CUDA、推論ランタイム (llama.cpp / ollama の CUDA 版) の入手経路。
- G-HW-7: NVIDIA ドライバと Secure Boot の両立 (署名済みモジュールがあるか、MOK 登録が要るか)。
- REL-1 / REL-2: 更新の失敗から戻す仕組み (何が戻り、何が戻らないか。特に /var、/etc、/home、ブートローダ、カーネルとモジュール)。ブートメニューから戻れるか。部品1つだけ戻せるか。
- MNT-2: パッケージやサービスの宣言を変えたとき、適用にかかる手順 (再起動が要るか、イメージのビルドが要るか、差分適用か)。
- INT-1 / INT-2: アプリが自分で書き換える設定ファイルと、宣言による管理が衝突するか。
- INT-3: 宣言されていない状態を一覧する仕組みがあるか。
- FLX-1 / FLX-2: 宣言の形 (パッケージ名の一覧か、独自言語か)。
- FLX-3: 無人インストール / 自動インストールの仕組み。
- SEC-3: 第三者ビルドの経路 (AUR、COPR、OBS home リポジトリ、flake など) と、その経路の既知の事件。
- MNT-4 / MNT-5: 定常の保守で必要な作業 (ニュースを読む、手動介入など)。公式が「手動介入が要る」と告知する頻度が分かれば。
- 道具そのものの健全性: 宣言ツール (decman など) の最終リリース日、メンテナ数。
