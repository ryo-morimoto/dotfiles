# Desktop: 目的と制約

版: 2026-10-23 v2。本文は手段に依存しない。手段は付録 A に分け、制約 ID で評価する。

---

## 0. この文書の読み方

```
目的 (1) ──> 成立条件 (2) ──> 制約 (3) ──> 優先順位 (4)
                                  │
                                  └──> 付録 A: 手段の評価 (制約 ID で採点。手段を替えるときは付録だけ書き換える)
```

**制約は、出どころで3つに分ける (互いに排他)**

| 区分 | 定義 | 変更 |
|---|---|---|
| **G 所与** | 外部から与えられた条件。設計では変えられず、変えるにはお金か時間がかかる | 状況が変わったときだけ |
| **P 選好** | 自分が決めて今は固定している好み。目的そのものではない | 見直しトリガーを満たしたら見直す |
| **Q 品質要求** | 目的から導かれる要求。ISO/IEC 25010:2023 の9特性で網羅する | 目的が変わったときだけ |

**Q の9特性と、重なりを避ける境界**

| 特性 | ここで扱うこと | 扱わないこと (行き先) |
|---|---|---|
| FUN 機能適合性 | 何ができるか | どれだけ速いか (PERF) |
| PERF 性能効率 | 速さ・資源の使用量 | 共存できるか (COMP) |
| COMP 互換性 | 同じ資源の共存と、他の系との相互運用 | — |
| INT 操作性 | 自分が日々触るときの扱いやすさ | 保守作業 (MNT) |
| REL 信頼性 | 壊れても使い続けられる、戻れる | 作り直し (FLX) |
| SEC セキュリティ | 機密性・認証・権限 | 物理的・不可逆な損害 (SAF) |
| MNT 保守性 | 意図した変更・更新のしやすさと速さ、定常の保守負荷 | 手段の乗り換え (FLX) |
| FLX 柔軟性 | 作り直し・乗り換え・ハード更改のしやすさ | — |
| SAF 安全性 | 不可逆な損害 (データ消去、ハード損傷) を防ぐこと | — |

**強さ:** MUST = 破ると目的が成り立たない。SHOULD = トレードオフしてよく、4章の優先順位に従う。MAY = あれば良い。
**数値:** 【仮】が付いた数値は提案値。5章で確定させる。

---

## 1. 目的

> **Desktop は、自分が直接触る唯一の作業面である。**

| ID | 目的 | 位置づけ |
|---|---|---|
| **O1** | 開発・調査・エージェントへの指示と監督を、**最小の注意コストで**、**最新の道具で**行える作業面 | 主 |
| **O2** | 手元の GPU を、ローカル推論資源として自分と Server に提供する | 従 (O1 を妨げない範囲で)【仮】 |

**非目的 (やらないこと)**

| ID | 非目的 | 行き先 |
|---|---|---|
| N1 | 常駐サービスのホスト | Server |
| N2 | データの唯一の保管場所になること | git / Server / バックアップ |
| N3 | 高可用性 (止まらないこと) | 止まっても他の系に影響しない設計にする (REL-3) |
| N4 | 他人と共有すること | — |
| N5 | クラスタのメンバーになること | Server とは API で接続する (7章) |

## 2. 成立条件 (WHEN / THEN)

| ID | WHEN | THEN | 主に関わる制約 |
|---|---|---|---|
| S1 | 電源を入れた | 日本語入力、2画面 144Hz、普段の道具がそのまま使える状態になる | FUN-1, PERF-4 |
| S2 | 使いたい上流の新版が出た | 自前でパッケージングせずに **N 日以内**に使える | MNT-1 |
| S3 | 日常の設定を変えた | 再構築も再起動もせずに即時反映される | INT-2 |
| S4 | パッケージやサービスの宣言を変えた | **分単位**で適用される | MNT-2 |
| S5 | 更新で壊れた | 別マシンなしで **M 分以内**に直前の状態に戻れる | REL-1 |
| S6 | ディスクが壊れた | 宣言から **H 時間以内**に同じ作業面を再現でき、失うデータが無い | FLX-3, REL-4 |
| S7 | Server のエージェントが推論を要求した | Desktop が起動していれば応答し、作業面の利用を妨げない | COMP-1, COMP-2 |
| S8 | 手段 (OS など) を替えると決めた | 設定・データ・宣言の大半を持ち越し、**D 日以内**に移れる | FLX-1, FLX-2 |

## 3. 制約

### 3.1 G 所与

| ID | 区分 | 制約 | 変更可能性 |
|---|---|---|---|
| G-HW-1 | CPU | i7-7700K、4コア / 8スレッド (x86-64-v3 相当)。7世代で古く、ビルドは遅い | 換装すると M/B ごと交換 |
| G-HW-2 | RAM | 16GB (8GB x2、DDR4-2400)。**4スロット中2つが空き** | 増設可 (要予算) |
| G-HW-3 | GPU | RTX 3060 Ti、**VRAM 8GB**、Ampere (CC 8.6)。GPU は1枚で、iGPU は無効。**作業面と推論が同じ GPU を使う** | 換装可 (要予算) |
| G-HW-4 | ストレージ | NVMe 1TB + HDD 2TB。どちらも全消去してよい | — |
| G-HW-5 | ディスプレイ | 1920x1080 / 144Hz が2台 | — |
| G-HW-6 | 入力 | JIS キーボード | — |
| G-HW-7 | ファームウェア | UEFI。Secure Boot は今は有効 (無効化できる) | — |
| G-ENV-1 | ネットワーク | 家庭 LAN + tailnet。Server 群と同じ LAN | — |
| G-ENV-2 | 利用者 | 1人。日本語ロケール | — |
| G-PPL-1 | 注意の予算 | 運用者は自分1人。保守に割ける注意は小さい (**週 X 分**)【仮】 | — |
| G-PPL-2 | スキル | Nix/NixOS は熟練。chezmoi / mise の運用経験あり | — |
| G-MON-1 | 予算 | ハードを追加購入できるかは未確定 | 5章 |
| G-LEG-1 | 法務 | CUDA と NVIDIA ドライバには NVIDIA の利用条件がかかる | — |
| G-EXT-1 | 上流 | コンポジタ、シェル、GPU ドライバ、推論ランタイムは更新が速い。DMS は 10月だけで 1.6.3 → 2.0.0 と動いた | — |
| G-EXT-2 | 上流 | 日本語入力 (hazkey) の配布経路が限られる (AUR / deb のみ) | — |

### 3.2 P 選好 (今は固定する。目的ではない)

| ID | 選好 | 根拠 | 見直しトリガー |
|---|---|---|---|
| P-1 | コンポジタはスクロール型タイリング (niri) | 操作感 | 開発が止まる、または NVIDIA で FUN-1 / PERF-1 を満たせない |
| P-2 | デスクトップシェルは DMS | 一体型で、自分で部品を組み合わせる手間が少ない | 大きな破壊的変更が続く、または G-EXT-1 の変化に追従できない |
| P-3 | 日本語入力は hazkey (mozc を補助) | 変換品質 | 配布が止まる |
| P-4 | ターミナルは ghostty、ブラウザは zen | 慣れ | — |
| P-5 | 状態を宣言的に管理したい | 再現性と手段の乗り換えのしやすさ | 宣言の程度は MNT / FLX で決める (P-5 自体は手段を指定しない) |

### 3.3 Q 品質要求

**FUN 機能適合性**

| ID | 強さ | 制約 |
|---|---|---|
| FUN-1 | MUST | P-1〜P-4 が動く: Wayland、2画面、144Hz、日本語入力、クリップボード、スクリーンショット、画面共有 |
| FUN-2 | MUST | 開発のツールチェーンとエージェント CLI (Claude Code / Codex / pi など) を使える |
| FUN-3 | MUST | GPU 計算 (CUDA) を使え、推論 API を提供できる |
| FUN-4 | SHOULD | GUI アプリ (ブラウザ、ノートアプリなど) を使える |
| FUN-5 | MAY | ゲーム (Steam) を使える【仮: 対象にするか要確認】 |

**PERF 性能効率**

| ID | 強さ | 制約 |
|---|---|---|
| PERF-1 | MUST | 作業面が常に使う VRAM は **≤ 0.5GB**【仮】。推論に 7GB 以上を残す |
| PERF-2 | SHOULD | 推論中も作業面の描画が 144Hz を保つ |
| PERF-3 | SHOULD | 作業面 + 開発 + 推論を同時に動かしても、swap を常用しない (RAM 16GB の範囲で。無理なら G-HW-2 の増設) |
| PERF-4 | MAY | 電源投入からログインできるまで 60 秒以内 |

**COMP 互換性**

| ID | 強さ | 制約 |
|---|---|---|
| COMP-1 | MUST | 作業面と推論が同じ GPU を共存して使える。推論側の負荷や VRAM 不足で作業面が落ちない |
| COMP-2 | MUST | Server に出す推論 API は標準的な形式 (OpenAI 互換など) にする。Server 側の手段に依存しない |
| COMP-3 | SHOULD | Server のサービスに、ノードではなく名前で届く |

**INT 操作性**

| ID | 強さ | 制約 |
|---|---|---|
| INT-1 | MUST | アプリが自分で書き換える設定 (GUI の設定画面) を書き込める。宣言による管理と衝突しない |
| INT-2 | MUST | 日常の設定変更は即時に反映される (S3) |
| INT-3 | SHOULD | 宣言されていない状態を1コマンドで一覧できる |

**REL 信頼性**

| ID | 強さ | 制約 |
|---|---|---|
| REL-1 | MUST | 更新に失敗しても、別マシンなしで **M 分以内**【仮 15分】に直前の動作状態へ戻れる |
| REL-2 | SHOULD | 1つの部品の不具合を、全体を巻き戻さずに戻せる |
| REL-3 | MUST | Desktop の停止・スリープ・再起動が、他の系 (Server) の可用性に影響しない |
| REL-4 | MUST | Desktop にしか無いデータを作らない (S6)。作業中のデータは git か Server かバックアップへ |
| REL-5 | SHOULD | 補助ディスク (HDD) が壊れても起動できる |

**SEC セキュリティ**

| ID | 強さ | 制約 |
|---|---|---|
| SEC-1 | MUST | 推論 API には、認証された相手 (自分の端末と Server のノード) からだけ届く。LAN 全体やインターネットには出さない |
| SEC-2 | MUST | 秘密情報を平文で宣言リポジトリに置かない |
| SEC-3 | SHOULD | 第三者がビルドしたものの入手元は最小限にし、一覧にしておく (サプライチェーン) |
| SEC-4 | SHOULD | Desktop で動かすエージェントの権限は、作業ディレクトリと許可した宛先に限る (Server と同じ方針) |

**MNT 保守性**

| ID | 強さ | 制約 |
|---|---|---|
| MNT-1 | MUST | **鮮度:** 指定した部品 (GPU ドライバ、CUDA、推論ランタイム、コンポジタ、シェル、日本語入力) は、上流のリリースから **N 日以内**【仮 7日】に、自前でパッケージングせずに使える |
| MNT-2 | MUST | パッケージやサービスの宣言を変えたら、全体を再構築せずに分単位で適用できる (S4) |
| MNT-3 | MUST | 宣言の置き場 (source of truth) は git の1か所 |
| MNT-4 | SHOULD | 定常の保守 (更新、確認、ニュースを読むこと) は **週 X 分**以内【仮 30分】 |
| MNT-5 | SHOULD | 上流の修正待ちの一時的な回避策を持たない。持つ場合は、不要になったら自動で検知して撤去できる |

**FLX 柔軟性**

| ID | 強さ | 制約 |
|---|---|---|
| FLX-1 | MUST | ユーザー設定とデータは、OS の管理手段から独立して持ち越せる (S8) |
| FLX-2 | SHOULD | システムの宣言は「パッケージ名の一覧 + ファイル + 有効にするサービス」という、手段に依存しない形に落とせる |
| FLX-3 | SHOULD | ゼロから再現するまで **H 時間以内**【仮 2時間】(S6) |
| FLX-4 | MAY | ハードの更改 (RAM 増設、GPU 換装) で、宣言の変更が数行で済む |

**SAF 安全性**

| ID | 強さ | 制約 |
|---|---|---|
| SAF-1 | MUST | 不可逆な操作 (ディスクの消去や初期化) は、対象を一意の ID で指定し、別のディスクを誤って消さない |
| SAF-2 | SHOULD | 長時間の推論負荷を、GPU と電源の温度・電力の上限内で回す |

## 4. 優先順位 (制約がぶつかったとき)

| 順位 | 制約 | 理由 |
|---|---|---|
| 1 | SAF、SEC-1、SEC-2 | 取り返しがつかない |
| 2 | FUN-1、COMP-1 | 作業面が使えなければ O1 が成り立たない |
| 3 | **REL-1 (戻れること) と MNT-1 (鮮度)** | **この2つの順位が手段選びの分かれ目** (5章 Q1) |
| 4 | MNT-2、INT-2 (変更が速いこと) | 今の不満の中心 |
| 5 | PERF-1〜3 (O2 のための性能) | O2 は従 |
| 6 | FLX、MNT-4 | 長期的な効率 |

**鮮度と戻りやすさの関係**
- 一般に、鮮度を上げるほど (更新を早く頻繁に取り込むほど)、壊れる回数が増え、戻す仕組みに頼る場面が増える [推論]。
- 「鮮度を優先し、戻る仕組みはほどほどでよい」なら付録 A の B 案、「戻れることを優先し、数日の遅れは許す」なら C 案に寄る。

## 6. 検証の仕方

| 制約 | 検証方法 |
|---|---|
| MNT-1 | 指定した部品ごとに「上流リリース日 → 自分の環境で使えた日」を記録し、N 日を超えた回数を数える |
| REL-1 | 月1回、わざと1つ前の状態に戻し、戻るまでの時間を測る |
| PERF-1 | 推論が止まっている状態で、作業面のプロセスが使う VRAM を測る |
| SEC-1 | LAN の別の端末と、tailnet の許可していない端末から推論 API に届かないことを確かめる |
| FLX-3 | 年1回か手段を替えるときに、空のディスクから再現し、かかった時間を測る |
| INT-3 / MNT-3 | 宣言されていない状態を一覧するコマンドの出力が空か、既知のものだけであること |

## 7. 外部インターフェース (Server との約束)

| 向き | 内容 | 約束 |
|---|---|---|
| Desktop → Server | 推論 API (OpenAI 互換) | tailnet 内だけ、認証された相手だけ (SEC-1)。**可用性はベストエフォート** (Server 側はつながらないときの代替経路を持つ) |
| Server → Desktop | 常駐サービス (コード置き場、タスク管理、観測) とエージェントの実行 | 名前で届く (COMP-3)。Desktop は Server の内部構成に依存しない |

## 付録 A: 手段の評価 (本文の制約 ID で採点する)

### A.1 候補と主な制約への適合 (2026-10-23 時点の根拠に基づく)

| 制約 | A. Fedora bootc (Zirconium-nvidia 派生) | B. Arch + decman + chezmoi + mise + snapper | C. NixOS 組み直し (上流 flake + CUDA キャッシュ) |
|---|---|---|---|
| MNT-1 鮮度 | △ COPR は即日だが、イメージの CI を通す | ◎ 公式リポジトリに即日〜数日 | △ チャネル遅延 (中央値 1.85日、最大 9.62日) + nixpkgs へのマージ待ち。flake で入れる部品だけ即日 |
| MNT-2 変更の速さ | × CI ビルド → 再起動 | ◎ 差分適用 (秒〜分) | △ 毎回 rebuild |
| REL-1 戻りやすさ | ◎ `bootc rollback` | △ snapper 頼み (/var の扱いに注意) | ◎ 世代 |
| REL-2 部分的に戻す | △ | ○ キャッシュ済みの旧版を入れ直す | ○ overlay |
| INT-1 GUI 設定の書き込み | ○ | ◎ | ○ (out-of-store symlink が要る) |
| FLX-1/2 持ち越し | ○ | ◎ パッケージ名の一覧なので中立 | △ Nix 式は Nix 固有 |
| SEC-3 サプライチェーン | ○ 署名付きイメージ | △ AUR (2026-06 に事件あり) | ○ |
| MNT-4 保守負荷 | △ CI と署名鍵 | △ ニュースを読む | ○ 慣れている |
| FUN-1 (hazkey) | × 自前ビルド | ◎ AUR が公式の配布経路 | ○ 今の flake |
| G-PPL-2 スキル | △ | ○ | ◎ |

**暫定の選択: B** (Q1 で鮮度が上なら B のまま。戻りやすさが上なら C)

### A.2 切り替えトリガー (手段に固執しないため、先に決めておく)

| 今の手段 | 切り替える条件 | 切り替え先 |
|---|---|---|
| B (Arch) | REL-1 を満たせない事例 (M 分以内に戻れない) が四半期に2回 | C |
| B の decman | 6か月更新が無い、または破壊的変更に追従できない | metapac / aconfmgr (宣言は Python の集合なので移しやすい) |
| B の DMS (extra) | extra の遅れで MNT-1 違反が3回 | AUR の `dms-shell-git` |
| C (NixOS) | MNT-1 違反が月2回以上、または一時回避策が常に1つ以上残る | B |
| どれでも | P-1 / P-2 の見直しトリガー (3.2) が発生 | 別のコンポジタやシェル (本文の制約で評価し直す) |

### A.3 どの手段でも共通に作るもの

- niri 設定の読み込み順: DMS ベース → default-binds → local.kdl → `dms/*.kdl`。DMS の設定画面が書く内容が勝つ (INT-1)。C 案の構成で `niri validate` を通して確認済み。
- NVIDIA の niri 向け VRAM プロファイル (`GLVidHeapReuseRatio=0`) を入れる (PERF-1)。
- 推論ランタイムの設定: flash attention と q8_0 の KV キャッシュ (PERF-1)、待ち受けは Tailscale のインターフェースだけ、ACL で相手を絞る (SEC-1)。
- ディスクは一意の ID で指定する (SAF-1)。

### A.4 既存の成果物

- `nixos-desktop-config.tar.gz` (C 案) は**廃止**。制約 v2 より前に作ったもので、SEC-1 (推論 API を LAN に公開している)、MNT-1 (NVIDIA が `stable` = 595、DMS が 1.6.3)、P-3 / P-4 (hazkey、zen が無い) に反する。C 案を選んだ場合は、制約 v3 から作り直す。再利用できるのは A.3 の共通部品と、確認済みの事実 (niri 設定の読み込み順が `niri validate` を通ること、CUDA 系がビルド済みキャッシュから取れること) だけ。
