# ADR-0007: Secure Boot は無効にする

日付: 2026-10-24。状態: 提案 (確認待ち)。

## 文脈

- G-HW-7: Secure Boot は今は有効で、無効にもできる。本文の制約に、Secure Boot を求めるものは無い。
- Arch の公式 ISO は Secure Boot で起動できない。インストールのときは、どのみち一度無効にする必要がある (Arch wiki)。
- 有効のまま運用するなら sbctl で自分の鍵を登録する。Arch のカーネルはモジュールの署名を強制しないので、nvidia-open は MOK の登録なしで読み込める見込みがある [推論。実機では未検証]。
- Limine は 11.2 以降、Secure Boot が有効だと設定のチェックサムの登録を強制する。登録を忘れると起動できなくなり、Secure Boot を切っても直らない (Arch wiki / CachyOS wiki)。limine-snapper-sync はスナップショットのたびに設定を書き換えるので、この失敗の機会が増える [推論]。
- 自分の鍵だけを登録すると、GPU の Option ROM が Microsoft の鍵で署名されている機種では起動しなくなることがある (Arch wiki)。

## 決定

Secure Boot は**無効にする**。インストールのときに無効にし、そのまま運用する。

## 満たす制約 / 満たせない制約

本文の制約には直接かからない。間接的には次の2つに効く。

- REL-1 / ADR-0002: Limine のチェックサムの登録忘れで起動できなくなる経路をなくせる。
- SAF: ファームウェアの鍵を書き換えずに済むので、Option ROM で起動しなくなる危険を避けられる。

## トレードオフ

- **得るもの:**
  - インストールと巻き戻しの経路が単純になる。
  - ファームウェアの鍵を書き換えない。
- **失うもの:** ブートチェーンの改ざんを検出できなくなる。物理的に触られる脅威と、ブートキットへの防御が弱まる。
  - この Desktop は1人で使い、手元にある (G-ENV-2)。この脅威は本文の制約に入っていない。必要なら制約として足すべき事柄である。

## 切り替えトリガー

| 条件 | 切り替え先 |
|---|---|
| Secure Boot を求める制約を足す (例: ディスク暗号化と TPM による解錠を組み合わせる) | sbctl で鍵を登録する (`-m` で Microsoft の鍵を残す)。Limine の設定チェックサムを limine-snapper-sync の更新に連動させ、D-V1 のモデルに「チェックサム不一致で起動しない」状態を足して検証し直す |

## 確認質問

- Secure Boot を無効にして運用してよいか。ディスク暗号化 (LUKS) を足したいか (ADR-0005 の「復号したファイルがディスクに残る」に関係する)。
